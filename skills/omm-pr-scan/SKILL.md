# omm-pr-scan — PR の差分だけ .omm/ を更新する

PR で変わったファイルを、既存の要素の担当パスに引き当て、当たった要素だけを `omm write` で更新する。全体を読み直す `/omm-scan` は回さない。起動は手動の `/omm-pr-scan` だけを想定し、`create-pr` などからは呼ばない。

`Base directory for this skill: <パス>` が起動時に渡される。以下ではそのパスを `<skill>` と書く。機械的な対応づけは `<skill>/scripts/map-changes.mjs` が行い、この手順書は判断と順番を受け持つ。スクリプトは依存パッケージを使わず、Node だけで動く。

```text
/omm-pr-scan
/omm-pr-scan main..HEAD
/omm-pr-scan main...HEAD
/omm-pr-scan --working
/omm-pr-scan --exclude 'src/generated/**'
```

## 最初に守る決まり

- 要素を足す・消すのは、ユーザーが承認したときだけ。案はまとめて一度に聞き、承認されたものだけを実行する。承認を待つのは「承認を待つ」の間だけ。
- 1 回の実行で、同じ要素の同じ項目を 2 度 `omm write` しない。図は図のファイル (`.omm/<要素パス>/diagram.mmd`) ごとに 1 度だけ書く。書く前に、そのファイルに入る変更をすべて集めて内容を決めきる。例外は `omm validate` の error を直すための書き直しで、同じ図につき 1 回まで。
- 要素の担当パスは、その要素自身ではなく、親の図 (`.omm/<親の要素パス>/diagram.mmd`) のノードのラベルに書かれている。末端の要素には図が無い。
- `.omm/` の変更は作業ツリーに残す。`git add`・`git commit`・`git push` をしない。
- `omm push` などのクラウド操作をしない。`omm view` を起動しない。PR にコメントしない。
- 新しい視点を作らない。既存の視点の中の要素だけを更新する。

## 手順

### 1. 前提を確かめる

次の 3 つを順に確かめる。1 つでも欠けたら、案内を 1 行出して止まる。ここで止まったら `.omm/` を 1 つも書かない。

```bash
command -v omm
git rev-parse --show-toplevel
cd "$(git rev-parse --show-toplevel)"
git ls-tree HEAD .omm
```

- `omm` が無い: `npm install -g oh-my-mermaid` を案内して止まる。
- `git rev-parse --show-toplevel` が失敗する (git リポジトリでない): リポジトリの中で実行するよう案内して止まる。
- ルートへ移ってから `git ls-tree HEAD .omm` を回す (パスはルートからの相対)。出力が空なら、先に `/omm-scan` を回し、`.omm/` をコミットしてから使うよう案内して止まる。比べる元 (HEAD の図) が無いまま書き始めない。

以降のコマンドはすべてリポジトリのルートで実行する。

### 2. 範囲を決める

引数は `[A..B | A...B] [--working] [--exclude <glob>]`。`--exclude` は何度でも指定できる。

- 範囲の引数は `A..B` か `A...B` (A と B の分岐点から B) だけを受ける。それ以外の形なら、使える形を案内して止まる。
- 範囲の引数 (`A..B`・`A...B`) と `--working` が同時に指定されたら、どちらか一方にするよう案内して止まる。

向き先 (base) と範囲は、次の順で決める。決まったら、以降のコマンドで使う値を `<開始>` と `<終点>` と呼ぶ。

1. 引数に `A..B` があれば、`A` を開始、`B` を終点にする。分岐点は使わない。`A...B` なら、開始を `git merge-base A B`、終点を `B` にする。
2. 範囲の引数が無ければ、開いている PR の向き先を取る。`gh` が無い・失敗する・PR が無いときは、エラーを無視して 3 へ進む。

   ```bash
   gh pr view --json baseRefName --jq .baseRefName
   ```

3. PR の向き先が取れなければ `develop`、それも無ければ `main` を base にする。どちらも無ければ案内して止まる。
4. base (2 で取れたもの、または 3 のもの) は、リモートの追跡ブランチを優先する。ローカルの base が古いと、他人の変更まで範囲に入るため。

   ```bash
   git fetch origin "<base>"
   git rev-parse --verify --quiet "origin/<base>"
   ```

   - `git fetch` が失敗しても (リモートが無い・オフラインなど) 止まらず、次へ進む。
   - `origin/<base>` があれば、それを `<基準>` にする。無いときだけ、ローカルの `<base>` (`git rev-parse --verify --quiet <base>`) を `<基準>` にする。どちらも無ければ案内して止まる。
   - 3 で `develop` と `main` のどちらを使うかを決めるときも、同じ順 (`origin/<名前>` → ローカル) で存在を確かめる。
5. 開始を `git merge-base <基準> HEAD`、終点を `HEAD` にする。`git merge-base` が失敗したら、理由を報告して止まる。

`--working` があるときは、終点を持たない。開始から作業ツリーまでの差を 1 回で取る (3 を参照)。これは追跡済みファイルの、コミット済みと未コミット (stage 済みを含む) の変更で、未追跡ファイルは入らない。

範囲には `.omm/` 自身の変更も入りうるが、対象外なので対応づけには使われない。

### 3. スクリプトで要素に引き当てる

`git diff` の出力をまずファイルに書く。`git` には `-c core.quotePath=false` を付け、日本語などのパスを引用符つきにさせない。ファイルは `.git/omm-pr-scan.changes` (git worktree でも使えるよう、`git rev-parse --git-dir` の下に置く。リポジトリの外の一時フォルダでもよい)。終了コードが 0 でなければ、`git` のエラーを報告して止まる。

```bash
f="$(git rev-parse --git-dir)/omm-pr-scan.changes"
git -c core.quotePath=false diff --name-status -M "<開始>" "<終点>" > "$f" || echo "git diff failed"
```

`--working` のときは、終点を付けず、2 つの diff をつながない。

```bash
f="$(git rev-parse --git-dir)/omm-pr-scan.changes"
git -c core.quotePath=false diff --name-status -M "<開始>" > "$f" || echo "git diff failed"
```

そのファイルを `map-changes.mjs` に渡す。`.omm/` のフォルダ、`--changes` のファイル、リポジトリのルートを指定する。出力は標準出力の JSON 1 つ。

```bash
node "<skill>/scripts/map-changes.mjs" --omm .omm --changes "$f" --root .
```

`--exclude '<glob>'` はそのまま何度でも足す。`--omm` は `.omm/` のフォルダ、`--root` は消えた担当パスを判定するリポジトリのルート。実行が終わったら `$f` は消してよい。

終了コードが 2 のときは、標準エラーに理由が 1 行出る。`--omm`・`--changes`・`--root` の指定を直して 1 度だけやり直す。直せなければ、理由を報告して止まる。壊れた出力のまま先へ進まない。

スクリプトは、`.omm/` 以下の各 `diagram.mmd` のノード定義 `id["..."]` のラベルを読み、最初の `\n` より後ろを担当パスにする。`,` と `、` で区切り、パスでない語 (`(外部・決済)` など) は捨てる。末尾が `/` ならフォルダ (前方一致)、`*` を含めば glob、それ以外はファイル (完全一致) として比べる。`class` 行・`classDef` 行・矢印のラベルはノード定義ではない。

当て方は視点ごと。一致した担当パスのうち、一番長いものを持つ要素を 1 つ選ぶ。同じ長さなら深い方、それでも同じなら辞書順で先。複数の視点に当たってよい。どこにも当たらなければ `unmatched` に入る。R は新しいパスで当て、視点ごとに新しいパスが当たらなければ、その視点だけ古いパスで当てる。

JSON は次の 5 つのキーを読む。

| キー | 読み方 |
| --- | --- |
| `matched` | ファイルごとに当たった要素。`status` は M / A / D / R (C は A)。R には `from` が付く。`elements` は視点ごとに最大 1 つで、複数の視点にまたがってよい。 |
| `renamed` | 名前変更で担当パスを書き換える要素と、変更前後のパス。承認は要らない。 |
| `unmatched` | どの要素にも当たらなかったファイル。AI が description を読んで判断する。 |
| `deletionCandidates` | D で当たり、担当パスが全部消えた要素と、その担当パス。消す案を出す。名前変更だけでは候補にならない。 |
| `excluded` | 対象外にしたファイルの数。報告に使う。 |

`matched` と `unmatched` がどちらも空なら、対象外を除いて変わったファイルが 0 件。何も書かずに「更新なし」と報告して終える (`excluded` の数は載せる)。

対象外の既定は、テスト (`**/*.test.*`・`**/*.spec.*`・`**/__tests__/**`・`e2e/**`)、ドキュメント (`**/*.md`・`docs/**`)、ロックファイル (`**/pnpm-lock.yaml`・`**/package-lock.json`・`**/yarn.lock`・`**/bun.lockb`)、`.github/**`、`.omm/**`、画像・フォント・3D モデル・音声などの静的ファイル (拡張子の大文字小文字は区別しない)。`package.json` などの設定ファイルは対象外にせず、当たらなければ `unmatched` に出す。`--exclude` はこの既定に足す。

### 4. 当たらないファイルと消す候補について、一度に聞く

`unmatched` か `deletionCandidates` があるときだけ、この段階で承認を取る。無ければこの段階を飛ばして 5 へ進む。

- `unmatched`: 候補になる親の `description.md` と `diagram.mmd` を読み、どの視点のどの要素の下に足すか (要素 ID・名前・担当パス) を決める。決められないファイルは推測せず、「対応なし」として報告に残し、承認の対象にしない。
- `deletionCandidates`: 消す案を要素ごとに出す。`paths` に残っている担当パスを添える。
- 足す案と消す案は、まず会話に番号つきの一覧で示す (例: `1. 足す: data-flow/new-cache (src/cache/)`、`2. 消す: data-flow/foo (src/foo.ts)`)。
- そのあと `AskUserQuestion` を **1 問だけ**聞く。選択肢は「すべて承認」「すべて却下」。番号での個別指定 (例: `1, 3 だけ承認`) は「Other」で受ける。案ごとに 1 問にしない (1 回に 4 問までしか聞けない)。
- ユーザーの答えを受けたら、承認された集合を控える。個別指定で触れられなかった案は却下とみなす。ここで受け付けるのはこの 1 回の答えだけ。要素の足し消しは 6 の中でだけ行う。

### 5. 変更を集める (まだ書かない)

書く前に、この実行で書くものを洗い出す。2 種類に分ける。

- **要素の項目** (`description` など、`omm write <要素パス> <field> -` で書く項目): (要素, 項目) ごとに 1 件。
- **図のファイル** (`.omm/<要素パス>/diagram.mmd`): ファイルごとに 1 件。その図に入る変更をすべてこの 1 件にまとめる。

次の変更を、該当する先に集める。

- `renamed`: 担当パスは親の図のノードのラベルにある。親 (要素パスの 1 つ上) の `diagram.mmd` を読み、その要素のノードのラベルの 2 行目 (最初の `\n` の後ろ) の `from` を `to` に直す。ラベルの名前と 1 行目は変えない。要素の `description.md` などにも `from` が書かれているなら、その項目も `to` に直す。承認は要らない。
- `matched` で `status` が D のファイル: 親の図のラベルの 2 行目から、その担当パスを外す。担当パスが全部消えた要素は、承認があるまで消さない。
- `matched` の要素: 変わったファイルのコードと、その要素の `description.md` などの項目を読み、コードと食い違う記述だけを直す項目を集める。要素が子を持ち自身の図があるなら、その図 (`.omm/<要素パス>/diagram.mmd`) で食い違う記述も同じく集める。同じ要素が `renamed` にも出ているときは、まとめて 1 件にする。
- 承認された「足す」: 新しい要素の `description` (子を持つならその要素の図も) と、親の図に足すノード・矢印。
- 承認された「消す」: 親の図から外すノードと矢印。`omm delete` は親の図のノードを消さないので、図の側でも外す。
- 親の図のつながり: 子の要素を更新して、子とほかの要素のつながり (矢印やノードの増減) が変わったと判断したとき。
- 子の担当パス: 上の `renamed`・D・足す・消すのように、親の図のラベルが変わるとき。説明が変わっただけなら、親の図は触らない。

図のファイルを洗い出すときは、同じファイルが複数の理由で入りうる点に注意する。ある要素の図は、その要素自身の図であり、同時に、その子たちの担当パスを持つ親の図でもある。同じファイルに入る変更は 1 件にまとめ、完成形 (既存のノード・矢印・`classDef` を保ったまま、変えるところだけを直したもの) を決めきる。`omm diff` は直前の 1 版としか比べられないため、同じ図を分けて書くと更新前との比較が失われる。

### 6. 書く (要素を更新する・親の図を直す)

5 で集めたものを、次の順で 1 度ずつ書く。承認された足す・消すは、この段階でだけ実行する。

1. 要素の項目: (要素, 項目) ごとに `omm write <要素パス> <field> -` に heredoc で渡す。1 項目 = 1 コマンドで、同じ Bash 呼び出しにまとめない。
2. 承認された「足す」: `omm write <新しい要素パス> description -` で要素を作る。新しい視点は作らない。
3. 図のファイル: 図のファイルごとに、完成形を `omm write <要素パス> diagram -` で 1 度だけ書く。親の図の書き直しもここで行う。
4. 承認された「消す」: `omm delete <要素パス>` を実行する。承認されなかった案は実行しない。`unmatched` のまま報告に残す。

書くときの決まり:

- 文章は `omm config language` の言語にそろえる。要素 ID・フォルダ名・ノード ID は英小文字のケバブケースにする。
- 図のノード ID は子のフォルダ名と一致させる。ラベルは 2 行形式 (`名前\n担当パス`) にし、担当パスはカンマ区切り、末尾が `/` ならフォルダ、それ以外はファイルとして書く。パスが無い外部の要素は 2 行目を `(外部)` のような説明にしてよい。
- 矢印には意味の分かるラベルを必ず付ける。`classDef` は omm 本体の手順書 (`omm-scan` スキル) の「Diagram Rules」の表にそろえる。
- 要素の中身を書き直すときの構成の分け方・項目の書き方は、同じく `omm-scan` スキルの「Diagram Rules」と「Step 3」にそろえる。丸写しはしない。
- 同じ要素に複数のファイルが当たったときは、内容をまとめてから書く。同じ項目を 2 度書かない。

### 7. 検証する

書いた図ごとに、その図を持つ要素パスで `omm validate` を回す。視点の図を書いたときは、視点名 (例: `overall-architecture`) で回す。引数なしの `omm validate` だけで済ませない (視点の図しか見ないため)。

```bash
omm validate <要素パス>
```

書いた図が 1 つも無いとき (項目だけを書いたとき) は validate を回さず、その旨を報告に書く。

- error があれば、該当する項目を直し、同じ要素パスでもう一度 `omm validate <要素パス>` を回す。同じ図を書き直してよいのは、この error を直すときの 1 回だけ。書き直したら、その旨を報告に書く。
- warning は直さず、そのまま報告に載せる。ノード数の warning は、omm v0.2.0 が空白を含む矢印のラベルまでノードとして数える誤検知なので、その注記を添える。
- 直しても error が残るなら、残った error と書いた内容を報告し、完了とは言わずに止まる。

### 8. 報告する

結果は会話にだけ出す。PR へのコメントなど外へ出す操作はしない。次の順で載せる。

1. 範囲: `A..B`・`A...B` の指定、または base (`origin/<base>` かローカルか)・分岐点・HEAD (`git rev-parse --short HEAD`)、`--working` の有無、`--exclude`。
2. 更新した要素の一覧: 変更・追加・削除・名前変更の別と、変えた項目。
3. 書いた図のファイルごとの更新前と更新後: その図を持つ要素パスで、`git show HEAD:.omm/<要素パス>/diagram.mmd` と `cat .omm/<要素パス>/diagram.mmd` を Mermaid のコードブロックのまま並べる。HEAD に無い図 (追加した要素の図) は更新前が無いと書く。末端の要素の説明だけを変えたときは、図の比較ではなく、変えた項目の名前を載せる。
4. `omm diff <要素パス>` の結果: 書いた図のファイルごとに、ノードと矢印の増減。
5. 当たらなかったファイル (`unmatched`) と、対象外にした数 (`excluded`)。
6. `omm validate <要素パス>` の結果: 直した error と、残った warning。
7. PR の本文に貼れる短い要約。例:

   ```markdown
   ## 構成の変更
   - 更新: overall-architecture/hooks (担当パスの追加)
   - 追加: data-flow/new-cache
   - 削除: なし
   ```

## 禁止事項

- `git add`・`git commit`・`git push` をしない。stage もコミットもしない。
- `omm push` などのクラウド操作をしない。
- `omm view` を起動しない。
- PR にコメントしない。結果を PR や外部へ送らない。
- 承認なしに要素を足す・消すことをしない。
- 新しい視点を作らない。
- error を直すとき以外に、同じ図のファイルを 1 回の実行で 2 度書かない。
